How to use this

This document has two readers: the human overseeing the work, and the agent workflow doing it. It is written to be handed to both.

Source-of-truth chain. Where these disagree, the higher one wins: (1) the owner's live instruction, (2) the CEO decision in §16 of the review — especially the below-the-line cuts, (3) the findings in §04, §07, §11, §12, §13, (4) this build plan, (5) the PRD's original schema and endpoint sketch. The PRD is deliberately last: §04 and §12 both found it incomplete, and an agent that treats it as authoritative will rebuild the gaps.

Ticket format. Every ticket carries an ID, an owner badge — agent for work an agent can complete and prove, human for work that requires a person, gate for the five items blocking public launch — and a done-when that is a command to run or an artifact to point at, never "looks right."

What this plan does not do. It does not re-open any decision from the review. If a stage looks like it's missing a feature you remember discussing, check §16's below-the-line table before adding it back — four things were cut deliberately, and they are the exact four an agent is most likely to helpfully restore.

One thing to authorize before Stage A. Every review to this point has been strictly read-only — no file under H:\Flourish App has been modified. Ticket A1 breaks that on purpose by initializing a git repository and committing the five screens unchanged as a baseline. That needs an explicit go-ahead, and it should be the first thing done rather than the first thing skipped: an agentic workflow without version control produces changes nobody can review, diff, or revert.
01

Delivery model — and the constraint that replaced capacity

§16 named the binding constraint as unconfirmed engineering capacity. That question is now answered, and answering it moved the constraint rather than removing it.
The new binding constraint is human review bandwidth, not engineering throughput. An agent can produce a week's worth of code in an afternoon. One person cannot meaningfully review a week's worth of code in an afternoon, and the failure mode isn't that they refuse — it's that they skim, approve, and the review becomes ceremonial. Every structural choice below exists to keep the volume of code requiring human judgment small enough that the judgment stays real.

The operating principle: convert review into test

Anything that can only be confirmed by a person reading code carefully is both a bottleneck and a risk. Anything confirmable by running a command is neither. So the plan front-loads the test harness and CI — items §13 rated "High, not launch-blocking" under a human-team assumption — because under this model they are not developer convenience, they are the review mechanism itself.

That single reordering is the most important difference between this document and the roadmap in §08. Under a human team, you can ship Phase 0 and add CI later. Under an agentic workflow, CI-first is what makes the rest of the plan safe to run at all.

Three tiers of verification — keep the third tier small

TierHow it's confirmedWhere it applies
MachineA test, linter, or script the agent runs and the human reads as pass/failDeletions, token conformance, alt-text presence, ownership scoping assertions, contrast ratios, build success. Most of the work belongs here.
Spot-checkHuman reads the diff; a miss is cheap and recoverableCopy changes, component extraction, styling, roadmap-scoped feature work.
PersonalHuman must do it themselves; an agent's report is not evidenceThe seven items in §10. Restore drills, keyboard passes, and anything where the agent grading its own homework is the whole risk.

The discipline is resisting tier drift. Work migrates upward — a spot-check becomes a glance, a personal verification becomes a report the human accepts. If tier three ever exceeds what one person can genuinely do in a sitting, the answer is to build more tests, not to lower the bar.

Agent concurrency, by stage

Parallelism is cheap and correctness is not, so fan out only where the work is genuinely independent. Stage B (deletions) and Stage D (accessibility, once components exist) parallelize cleanly per file. Stage C is a serial choke point by nature — five agents extracting shared components from five files simultaneously will produce five incompatible component libraries, which is the exact divergence §07 already found once. Stage E's authorization work should run single-threaded and slowly, regardless of what the tooling permits.

# Flourish — working rules

Read `docs/REVIEW.md` (§16) before proposing scope. This file is the short version.

## Do not re-add these — they were cut on purpose

- **Turn-by-turn navigation.** "Start Navigation" hands off to Apple/Google Maps
  via a maps: URL. We are not building navigation. Mapbox Directions is in scope
  ONLY for drive-time estimates between itinerary stops.
- **Drag-reordering on Trip Planner.** The Reorder control is removed, not
  reimplemented. Do not restore it because the list "looks like" it should sort.
- **Community sharing of private gems.** No sharing UI, no "Coming Soon" label,
  no public/private visibility switcher beyond the schema column. There is no
  moderation model, so there is no feature.
- **Offline map caching.** Deferred. The simulated "42 MB downloaded" toast is
  deleted — never re-add a progress indicator for a download that isn't happening.

If a ticket seems to require one of these, stop and ask. Do not infer.

- The root `DESIGN.md` is the ONLY source of color, type, spacing and radius
  values, and specifically its YAML **frontmatter** — the prose section below it
  is documentation, not the token source. Generate tokens from the frontmatter;
  never hand-write a hex in a component.
- Two other byte-identical copies exist at `flourish_roc_lakes/DESIGN.md` and
  `trip_planner_flourish/DESIGN.md`. C1 deletes them. Do not edit or read them.
- C2 is decided (2026-09-09): the brand is Deep Lake Navy `#162A45` primary and
  Rochester Lilac `#7E57C2` secondary — the prose values, not the frontmatter's
  original `#00152f`/`#6f48b2`. C1 rewrites the frontmatter to match. If you

03

Sequencing map

What must be serial, what can fan out, and the two places where getting the order wrong costs more than the work itself.
STAGE A
serial
Repo, guardrails, harness, CI

Blocks everything. No agent work should happen before A5 is green — until CI runs, there is no way to tell a good change from a plausible one.

STAGE B
parallel ×5
Deletions — the approved cuts and Phase 0 hygiene

Pure removals, one agent per screen. Safe, fast, and a good calibration run for the workflow before anything additive happens.

STAGE C
SERIAL — choke
One token system, one component library, one taxonomy

Do not parallelize this. Five agents extracting shared components at once produce five incompatible libraries. One agent, one pass, everything downstream depends on the result.

STAGE D
parallel ×5
Accessibility remediation, per screen

Only after C. Fixing alt text and focus states on five files that are about to be replaced by shared components is work done twice.

STAGE E
SERIAL — choke
Schema → auth → ownership tests → endpoints

The ownership test suite is written before the endpoints, and the human writes or approves its assertions. Endpoints may then fan out; authorization logic may not.

STAGE F
parallel
Backups, observability, secrets

Can run alongside D and E. The restore drill at the end is human-only and is the gate, not the backup configuration itself.

The two orderings that actually matter: taxonomy before schema before endpoints (§04 — three competing category lists, and every downstream API shape depends on which one wins), and components before accessibility (§07 — otherwise the same nine WCAG fixes get made five times and diverge again on the sixth screen).

Stage D — Accessibility

The nine §11 findings plus the zoom-lock already handled in B1. Two of these are launch gates. Parallelizes per screen once Stage C's components exist — and much of it is already fixed by C4 if that component work was done properly.
The automated scan is a floor, not the bar. axe-core in CI catches a minority of WCAG issues — commonly estimated at around a third — and every one it misses is the kind that needs a person. A clean axe run means the obvious defects are gone. It does not mean the app is usable by a screen-reader user, and no agent can tell you that it is. The manual passes in §10 are what actually close this stage.
D1
agentgate

Real alt text on every meaningful image (WCAG 1.1.1)

The screens use a data-alt attribute instead of alt — meaningful photography is currently invisible to screen readers. Write descriptions that convey what the image contributes: the destination, the setting, the thing a sighted user takes from it. Purely decorative images get alt="", and only those.

Done when axe reports zero image-alt violations AND a human has read the alt list once — see §10, item 4. This ticket cannot be closed by the scan alone.
D2

Done when tabbing through every screen shows a visible indicator at each stop, confirmed by the human keyboard pass in §10.

08

Stage E — Backend & the security gate

The stage to run slowest. §12's critical finding — no ownership scoping on the private-gem endpoints — is exactly the class of bug an agent writes plausibly and a tired reviewer approves. The structure below is designed so the human never has to catch it by reading.
Vendor picks land here, not earlier. Which managed Postgres, which auth provider, R2 versus S3, which hosting platform — none of these were decided in advance, on purpose. Per §02: get something working first, matching the direction already set (managed Postgres+PostGIS, bought auth wrapping Apple/Google, object storage behind a CDN, Mapbox), and treat any of it as revisable once real usage says otherwise. The human creates each account personally and hands the agent a scoped key — no agent provisions a paid account itself.
Tests before endpoints, and the human writes the assertions. E4 comes before E5 deliberately. Rather than asking one person to carefully review authorization logic across a dozen endpoints — the thing humans are worst at and agents are most confidently wrong about — the human writes a small suite that asserts user A cannot read, update or delete user B's gems by any route, and agents implement against it. That converts §12's critical finding from a review burden into a red test, which is the only version of this that stays true after the tenth endpoint.

The non-delegable list

Seven things the one human must do personally. Everything else in this plan can be delegated to agents with a test to prove it. This list is deliberately short — a long one gets skimmed, and a skimmed list is the same as no list.
#WhatWhy an agent's word isn't enough
1Authorize and make the A1 baseline commitIt's the point where this project stops being read-only. Worth doing consciously rather than discovering it happened.
2Write or approve E4's ownership assertionsAn agent writing both the authorization code and the test that proves it is grading its own homework on the one finding that breaks the product's only privacy promise.
3Read every diff touching auth or user_private_gemsThe one place in this plan where careful human reading is still worth its cost. Keep these PRs small enough that it's possible.
4Read the alt-text list once, end to endThe likeliest agent failure in the whole plan: alt="" on meaningful photos passes every automated check and fails every screen-reader user. Only a person reading the descriptions catches it.
5Keyboard-only pass on all five screensTab through everything, activate everything, escape every modal, with the mouse untouched. Automated scanning cannot tell you the tab order is sensible or that focus isn't trapped.
6Screen-reader pass on the two critical flowsSaving a private gem and building an itinerary, with VoiceOver or TalkBack on. If those two are usable, §11's gate is genuinely closed rather than technically closed.
7Perform the F2 restore drillBackup configuration and recovery capability are different claims. Only one has ever saved anyone.

Items 4 through 6 are the accessibility gate in §14. They are the reason that gate cannot be closed by a green CI run, and they are worth roughly a focused afternoon in total — a small price for the one thing the owner named as integral to the whole design.

What agents get wrong here

Not generic cautions — the specific failure modes this codebase and this plan invite. Each is worth a guardrail, a test, or a place on the non-delegable list, and each already has one.

Helpfully finishing what was deliberately cut

A fresh agent reads the repo and sees a Reorder button with no handler, a download toast with no download, and a "Coming Soon" label with nothing behind it. It correctly identifies all three as incomplete and completes them — reversing three CEO decisions while behaving exactly as designed. Countered by: §02's guardrails, stating each cut with its reason, plus tests that assert absence rather than presence.

Silencing the accessibility linter instead of fixing the problem

Told that axe must pass, the cheapest path to green is alt="" on every image. That satisfies the tool completely and makes the app worse for the users the ticket exists to serve — a false pass that reads as a real one on the dashboard. Countered by: D1's done-when requiring a human read, and non-delegable item 4. This is the single most likely way this plan produces a technically-compliant, practically-inaccessible app.

Getting authorization right in four endpoints out of five

Ownership filters applied per-handler are correct until someone adds a handler. The gap is invisible in review because each individual file looks right. Countered by: E5 enforcing scope in one layer — repository or row-level security — and E4's suite covering every route rather than a sample.

Inventing colors, exactly as happened the first time

§07 found the brand's documented navy absent from all shipped code. That drift came from picking values in components instead of from the system, and an agent generating a new component will do the same thing at higher speed. Countered by: C1's generated tokens and A4's conformance test failing on any stray hex.

Reporting a test as passing without running it

Common, and it defeats the entire tier-one verification model this plan rests on. Countered by: CI being the source of truth from A5 onward — the human reads the pipeline, not the agent's summary of it. If those two ever disagree, the pipeline is right.

Reformatting a file while fixing one line in it

A 900-line diff containing one real change is unreviewable, and unreviewable diffs are where the other five failure modes hide. Countered by: §02's small-diff rule and a committed formatter config so formatting is never a per-agent opinion.

Estimate & definition of done

§14 estimated 3–5 weeks against an assumed small human team. That figure measured the wrong thing for this delivery model and should be replaced rather than adjusted.
Count human checkpoints, not engineer-weeks. Agent throughput no longer sets the pace, so a week-based estimate mostly measures how often the overseer sits down. The honest unit is checkpoints: roughly 12–15 sessions where the human reviews, decides or personally verifies something. At one focused session most days that is about two and a half to three weeks; at a few sessions a week it is six or more. Neither is wrong — but the number is set by the human's calendar, not by the work.

Definition of done — public launch

All five §14 gates closed, each with its evidence rather than its assertion:

  • Private-gem ownership — E4's suite green in CI, and confirmed red when scope is deliberately removed.
  • Backups and restore — F2's drill performed by the human, with elapsed time written into the runbook.
  • Observability — a real error in the dashboard and a real alert on a real device.
  • Alt text and focus states — axe clean, plus non-delegable items 4, 5 and 6 completed.
  • Phase 0 hygiene — Stage B complete and Stage C's tokens and taxonomy each reduced to one source.

Plus the model-specific addition: CI has been green on every merge for the stretch preceding launch. Under a human team that would be a nicety. Here it is the evidence that the verification model held — and if the pipeline was routinely red or bypassed, then the plan's central assumption failed quietly and the gates above are claims rather than facts.

What would change this plan. If Stage B produces sprawling diffs, out-of-scope changes, or restored features, stop and fix the guardrails before Stage C — that is what Stage B is for, and it is much cheaper to learn there than in Stage E. If the human checkpoints start slipping or getting rubber-stamped, the constraint from §01 has become binding in the way it was designed to prevent, and the response is fewer parallel agents rather than faster reviews.
