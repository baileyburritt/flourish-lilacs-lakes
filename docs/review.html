Brief

Scope reviewed: flourish_lilacs_lakes_technical_handoff_prd.md (data model, API sketch, integrations), flourish_roc_lakes/DESIGN.md (token system), and the five exported prototype screens — Explore & Curate, Music & Live Events, Trip Planner, Destination Detail & Private Gem, and the standalone New Private Gem flow. Each screen is a self-contained AI-exported HTML file (Google Stitch output, judging by the lh3.googleusercontent.com/aida image hosts and the sibling stitch_rochester_finger_lakes_explorer.zip) — no shared repo, no framework, no build step yet.

Method follows two disciplines in parallel: technology:solution-architecture for the backend and stack recommendation, and product:ux-product-auditor / product:interface-redesign for the walk-through of what's built. Every finding below names where it lives and what it costs — no unranked style notes.

01

Executive summary

The five screens are a design proof, not an app. There is no API, no database, no auth, and nothing survives a page refresh — every "save," "bookmark," and form submit is a DOM mutation that vanishes on reload. That's expected and fine for what these files are for. It stops being fine the moment anyone treats them as more than 80% done.

Two things need attention before engineering starts building against the PRD's schema: the schema itself undercounts what the designed screens already promise to capture (§04), and the design system's canonical document contradicts itself — DESIGN.md's frontmatter and its prose specify different palettes, the code implements the frontmatter, and the brand's lilac accent survives in prose only (§07). Neither is expensive to fix now. Both get expensive once a backend and real users are on top of them.

Read this first if short on time: §04 (data model gaps) and §07 (systemic findings) affect every screen and every future one. Fix those before writing the next screen, not after.

Backend architecture & stack plan

Per technology:solution-architecture — stated constraints first, then boundaries, then the trade-off each option makes.

Constraints assumed (none were supplied — confirm before committing)

Single-region regional travel app (Western NY), early-stage — hundreds to low-thousands of concurrent users at launch, not tens of thousands. Small team, likely 1–3 engineers. No stated compliance obligation beyond standard user PII (email, location history, photos). Mobile client target is iOS/Android/PWA from one codebase per the PRD header. If any of that is wrong, the recommendation below should change with it — see §09.

LayerRecommendationWhy / what it costs
ClientReact Native (Expo) for iOS/Android; the existing screens rebuilt as a shared component library, not five bespoke pagesOne codebase covers both stores plus a web build via Expo's web target, which also satisfies the PWA line in the PRD without a second front end. Costs: React Native's native-module edge cases (deep GPS/offline map work) take longer than pure native would.
APIREST over a small managed Node (NestJS) or Rails service — not GraphQL yetThe PRD's endpoint sketch (§3) is already resource-shaped REST. GraphQL earns its cost when clients need to compose many nested resources per screen; five screens with well-known shapes don't. Revisit if a public/partner API shows up later.
DatabaseManaged PostgreSQL (Neon, Supabase, or RDS) — the PRD's schema in §2.2 is a workable starting point once §04's gaps are closedRelational fits the domain (users → trips → stops → destinations, all genuinely relational). PostGIS extension for lat/long queries ("destinations near me") rather than hand-rolled bounding-box math.
AuthManaged auth (Clerk, Supabase Auth, or Auth0) wrapping Apple/Google sign-inPer chief-technology-officer's build/buy rule: auth is undifferentiated — nobody chooses Flourish for its login screen. Buying it also buys OAuth compliance work the team would otherwise own.
Asset storageCloudflare R2 or S3 + CDN, replacing every lh3.googleusercontent.com referenceR2 skips egress fees, which matters once destination galleries and user gem photos are real traffic. Matches the PRD's own §5.3 recommendation.
MapsMapbox GL + Directions API, as the PRD specifiesNo change recommended — Mapbox's rural/scenic-route directions quality is the right fit for Finger Lakes drives; Google Maps SDK is the fallback if Mapbox pricing becomes a problem at scale.
HostingA managed platform (Render or Fly.io) for the API, not self-managed KubernetesPer cloud-infrastructure: "managed application platforms are the right answer more often than engineering pride admits." Kubernetes is a platform team's worth of work this team doesn't have yet.
EnvironmentsThree: dev, staging, production — separate databases, staging seeded with synthetic data onlyNo production data in staging, ever, even for a two-person team. It's the cheapest incident to prevent and the most common way user PII leaks.
What this costs: Managed services trade a monthly bill for not operating Postgres, auth, or Kubernetes by hand. For a pre-launch regional app, that trade is almost certainly right — the alternative is spending engineering time on infrastructure instead of the itinerary and discovery features that are the actual product. Revisit self-hosting only if usage and cost data say the managed premium has become the larger number.
04

Data model gaps

The PRD's user_private_gems schema (§2.2) was written before — or without reference to — the two screens that actually capture a gem. They don't match.

Three incompatible category taxonomies for one concept

Critical

Where: PRD §2.2 destination_category enum vs. destination_detail_private_gem_flourish/code.html vs. new_private_gem_flourish/code.html.

What: The PRD schema reuses a 6-value enum (WINERY_BREWERY, NATURE_WATERFALLS, CULTURAL_HISTORIC, DINING_MARKETS, LIVE_VENUE, CIVIC_LANDMARK) for private gems. The inline "Log a Personal Hidden Gem" form on the destination-detail screen uses a five-value set instead (Scenic View, Hidden Trail, Food & Drink, Craft Shop, Live Acoustic). The standalone New Private Gem screen uses a seventh, entirely different seven-value set with emoji glyphs (Scenic Overlook, Quiet Kayak & Swim, Roadside Stand, Secret Cidery, Acoustic Busker Spot, Hidden Garden Patio, Unmarked Trailhead). None of the three lists overlaps cleanly with either of the others.

Consequence: Whichever form a user fills out first determines a category value the backend can't reconcile with a category filter written against the PRD enum. Filtering "My Spots" by category will silently miss gems saved through the other flow.

Fix — Pick one canonical gem taxonomy (recommend expanding the PRD enum, since it's the one the database and any cross-content filtering depends on), then reconcile both forms to emit it. This is one root cause behind what would otherwise read as three separate findings — fix the taxonomy once, both screens inherit the fix.

Two free-text location fields, one schema column

High

Where: user_private_gems.location_hint (PRD §2.2) vs. New Private Gem screen's two separate inputs — #location-input ("42.6074° N, 77.6892° W") and an unlabeled landmark-clue text field ("Take rustic path 35 yards past the old stone weir gate").

Consequence: One of the two inputs has nowhere to go without a schema change; if a backend maps both into one column, the landmark clue and GPS override get silently merged or one gets dropped.

Fix — Split location_hint into landmark_note TEXT and keep latitude/longitude for the GPS pair, which the schema already has as separate columns — the UI just isn't writing to them as such.

Season and "magic hour" metadata: designed, unmodeled

High

Where: New Private Gem screen, "Seasonal Peak & Timing" section — four season chips, four time-of-day chips.

Consequence: This is a differentiator for a seasonal-discovery product (the whole app leads with "Highland Park Lilac Season" as a hero feature on Explore) and has no column to land in. If this ships against the current schema, the feature silently no-ops.

Fix — Add ideal_season and golden_hour enum columns to user_private_gems, or fold them into the existing metadata JSONB column on destinations if this is meant to generalize beyond private gems.

Audio memo capture has no storage target

Medium

Where: New Private Gem screen — "Memo (0:14)" recorder button and playback row for Field_Audio_Stream_Notes.m4a.

Consequence: No audio_url equivalent exists anywhere in the PRD schema, and audio isn't mentioned in §5 (asset storage) either. Confirmed in-scope per product direction (§14) — this is a gap to close, not a candidate to cut.

Fix — Add an audio_url column to user_private_gems and cover it under the same signed-URL access-control plan Security recommends for gem photos in §12 (audio memos are the same class of private, potentially sensitive user content). Scheduled into Phase 1 (§08), not deferred to Phase 2.

"Flower City (ROC)" is a boolean, but the UI treats it as a category

Medium

Where: PRD §2.2 destinations.is_flower_city_waypoint BOOLEAN vs. the Explore screen's filter chip bar, where "Flower City (ROC)" sits alongside category chips like "Waterfalls & Gorges" and "Wine & Craft Breweries" as if it were one more category.

Consequence: A destination can be both a winery and a Flower City waypoint — the filter UI as built can't express "show me both," because it's wired as a single-select chip row, not a boolean toggle plus a category filter.

Fix — Split the filter bar into two independent controls: a category selector (single-select, from the real enum) and a Flower City toggle (boolean, can combine with any category).
05

API contract notes

Per technology:api-design — the PRD's endpoint sketch (§3) is a reasonable start. Three things to fix before the first client integrates against it, because all three are breaking changes once someone depends on the current shape.

Pagination is offset-based. GET /api/v1/destinations takes limit, offset. Events and destinations are both collections that grow and get written to concurrently (new events posted weekly). Offset pagination skips and duplicates rows under concurrent writes — switch to cursor pagination now, before any client hard-codes offset math.

No documented error shape. The PRD spec shows only success responses. Add a consistent error envelope (machine-readable code, human message, retryable flag) before the mobile client writes its first error handler against whatever shape the server happens to return today.

Bookmark/RSVP endpoints don't say what they return. POST /api/v1/events/{id}/bookmark is described as "toggle state" — toggle endpoints are a common source of lost-update bugs on flaky mobile connections (double-tap while offline, retry, state flips twice). Make it idempotent: accept an explicit desired state, or make bookmarks a proper sub-resource with PUT/DELETE.

07

Systemic findings

Per interface-redesign: fifteen findings traceable to one root cause are one finding. These four affect every screen, current and future.

DESIGN.md contradicts itself, and the code follows only half of it

Critical

CORRECTED 2026-09-09 — see the amendment note below this finding.

Where: DESIGN.md carries two palettes that disagree with each other. Its YAML frontmatter defines primary: #00152f, primary-container: #162a45, secondary: #6f48b2. Its prose section, forty lines below, names different values for the same roles: primary #162A45 "Deep Lake Navy," secondary #7E57C2 "Rochester Lilac," canvas #F8FAFC, plus a "Lake Slate" neutral #475569 that exists as no token at all. The PRD header repeats the prose values.

The Tailwind config embedded in all five HTML files matches the frontmatter exactly, token for token. So the shipped code is not drifting from its documentation — it is faithfully implementing one half of a document that disagrees with the other half. Two consequences follow that are easy to state the wrong way round: the documented brand navy #162a45 is present in all five files, demoted to primary-container while the darker #00152f holds primary — but the lilac accent #7e57c2 is genuinely absent from both the frontmatter and every shipped file, surviving only in prose.

Also drifted — the radius scale, shifted by one step. Frontmatter rounded is sm/DEFAULT/md/lg/xl = 0.25/0.5/0.75/1/1.5rem; the shipped Tailwind config is DEFAULT/lg/xl = 0.25/0.5/0.75rem, dropping sm and md and renaming the rest downward. A rounded-lg in code is half the radius DESIGN.md calls lg. Typography and spacing tokens match cleanly and did not drift.

Consequence: There is no single source of truth, and the failure is worse than a stale doc — the canonical document is internally inconsistent, so "check DESIGN.md" produces a different answer depending on which half is read. A designer reading the prose and a developer reading the frontmatter both believe they are following the system. Compounding this, DESIGN.md exists as three byte-identical copies (repo root, flourish_roc_lakes/, trip_planner_flourish/), and the full token block is duplicated verbatim into all five HTML files — five places to edit, and no mechanism preventing the sixth from diverging.

Fix — Resolve the contradiction inside DESIGN.md first: decide whether the frontmatter or the prose is the brand, then rewrite the loser to match. That is the actual decision, and it is a brand call — the code is downstream of it either way. Then collapse the three copies to one, generate the token block from it rather than hand-maintaining five, and reconcile the radius scale in the same pass regardless of which side wins the color call — the prose's own radius language already agrees with the frontmatter's scale, so that fix is owed to the code either way. If the prose wins, the additional code change is restoring the lilac accent. If the frontmatter wins, no component touches color at all — only DESIGN.md's prose is rewritten, to describe the values already shipping.
Amendment — what the original finding got wrong. As first published, this finding was titled "the brand's signature accent color doesn't exist in the shipped code" and described #00152f as "undocumented." Re-checked directly against the files on 2026-09-09: #00152f is documented — it is DESIGN.md's own frontmatter value for primary — and #162a45 ships in all five screens as primary-container. The original framing of code-drifting-from-docs was therefore wrong in direction: the code matches the frontmatter exactly, and the contradiction lives inside DESIGN.md. The lilac-accent half of the finding stands as filed — #7e57c2 appears in prose only. The radius shift and the three-copies duplication were missed entirely on the first pass and are added above. Severity is unchanged: a self-contradicting source of truth is at least as serious as a stale one. §01's summary and the build plan's C1/C2 tickets have been corrected to match. This fix paragraph also had the frontmatter/prose cases reversed on first correction — fixed above on the same pass that decided C2 (below).
Decided 2026-09-09 — the prose is the brand: Deep Lake Navy and Rochester Lilac. The owner ruled on C2, revising an earlier same-day call for the frontmatter once its consequence became visible: DESIGN.md's prose wins, not its frontmatter. Unlike the frontmatter option, this is a real re-render — all five screens change color, not just the documentation — but it has a practical point in its favor: §10 below found the approved logo file, flourish_logo.png, already rendering its subtitle in exactly this lilac. Pinch-to-zoom disabled on every screen

Critical

Where: <meta name="viewport" content="...maximum-scale=1.0, user-scalable=no">, identical in all five files.

Consequence: Blocks pinch-zoom for anyone who needs to enlarge text or a map beyond the app's fixed sizes — a WCAG 1.4.4 failure, not a style preference. This is a category of user excluded outright, per the accessibility lens in ux-product-auditor.

Fix — Remove maximum-scale=1.0, user-scalable=no from the viewport meta everywhere. No functional reason found in any of the five screens to justify disabling it.

No shared components — everything is copy-pasted five times

High

Where: header, bottom nav, and the full Tailwind token config (~2.5KB of JSON) are duplicated verbatim in all five files.

Consequence: This is how the Music screen's missing active-tab state (§06) happened — one of five copies drifted. It will keep happening at this rate of one bug per few screens as more get added.

Fix — First real engineering task once client framework (§03) is chosen: extract <Header>, <BottomNav>, and the design tokens into shared components/files, single-sourced.

Nothing persists — every interaction resets on reload

High

Where: bookmark toggles, filter selection, checklist state, the "add gem" toast confirmations — all DOM-only, none written anywhere.

Consequence: Expected for a design prototype; called out because it's easy to demo these screens, watch bookmarking "work," and underestimate how much is left. Every green checkmark in a demo today represents zero backend work done.

Fix — No action needed on the prototype itself; treat every interactive affordance across all five screens as unimplemented for estimation purposes, not partially done.

09

Assumptions & what would change this

Assumptions this plan depends on: early-stage traffic (not enterprise scale), a small engineering team, single-region operation, and no compliance regime beyond standard consumer PII handling. The stack recommendation in §03 is sized to those.

What would change the recommendation: a confirmed multi-region or high-concurrency launch target would push toward a more horizontally-scaled API tier sooner; a partner/B2B API surface would revive the GraphQL question deferred in §05; a decision to keep private gems permanently on-device (rather than "coming soon" community sharing) would remove most of the sync-conflict design work otherwise owed to that table.

Handoff: engineering owns Phase 0 token/schema reconciliation before any new screen is designed against the current PRD; product/design owns picking the canonical gem taxonomy, since that choice is user-facing, not just a database decision.

Meaningful photos are invisible to screen readers — data-alt used instead of alt

Fix — Rename data-alt → alt on every <img>; convert background-image divs to real <img> tags or add role="img" aria-label="…". Mechanical, one pass across five files.

Security architecture review

Per security:security-architecture-review, threat-modeling, and data-protection-and-encryption — a review of Technology's proposed backend plan (§03) and the data model it's meant to serve (§04), not of code that exists yet. Read-only; nothing here required touching a file beyond the PRD and DESIGN.md.
Blocking finding: the PRD's endpoint sketch never states that private-gem endpoints scope to the authenticated owner. That's the one gap serious enough to hold sign-off on until Technology confirms it in writing — see below.

No described ownership scoping on the private-gem endpoints

Critical

Where: GET/POST /api/v1/gems/private, user_private_gems table.

What: The spec never states these endpoints filter by user_id from the auth token rather than a client-supplied identifier. This table is the app's single most sensitive dataset — precise coordinates, notes, and photos for spots the UI itself brands "Vault Mode" and promises are private.

Consequence: If authorization is checked only "on the way in" (valid token) and not against the record's owner, any authenticated user can enumerate gem IDs and read other users' hidden locations, notes, and photos — a direct breach of the app's one explicit privacy promise, and an irreversible one.

Fix — Every gem query/mutation filters WHERE user_id = auth.user_id at the query layer, enforced by an automated authorization test, not a code-review assumption.

is_private is a mutable flag on the live table, pre-annotated for a future public migration

High

Where: user_private_gems.is_private (schema comment: "Configured for future community sharing migration").

Consequence: Privacy is a boolean on the same row as the sensitive data, not a structural boundary. One migration bug or careless bulk-update when the sharing feature ships flips every user's secret spots public simultaneously — a single-event mass disclosure, not a gradual leak.

Fix — Treat "share publicly" as an explicit, per-record, user-initiated action with its own audit trail before any migration touches this column; never default schema changes to public.

No access-control scheme described for gem photos in object storage

High

Where: photo_urls → planned R2/S3 + CDN (§03).

Consequence: CDN-fronted buckets are typically public-read by default. Even with endpoint-level authorization fixed, a photo of a "secret" spot becomes reachable to anyone with the URL, and predictable object keys make URLs guessable.

Fix — Serve private-gem photos only via short-lived signed URLs, in a bucket/prefix separate from public destination imagery.

No rate limiting anywhere, including unbounded photo uploads

Medium

Where: All endpoints; photo_urls has no stated per-gem/per-user cap.

Consequence: Unbounded uploads invite storage/CDN cost abuse; unthrottled auth endpoints invite credential stuffing against the managed-auth provider.

Fix — Rate-limit at the API gateway/managed-auth layer; cap photo count and size per gem.

No account-deletion or data-retention policy documented

Medium

Where: users cascades to trips and user_private_gems at the DB level, but nothing addresses orphaned object-storage photos after a row delete, or a user-facing deletion flow.

Consequence: Apple requires in-app account deletion for apps with account creation (App Store Guideline 5.1.1(v)) — missing this blocks store approval outright, separate from any exposure from precise location and email data lingering indefinitely.

Fix — Build an account-deletion endpoint that cascades DB rows and issues object-storage deletes for associated photos; document a retention window.

"No prod data in staging" is a stated rule with no enforcement mechanism

Low

Where: Environment plan (§03).

Consequence: Under deadline pressure, someone eventually restores a prod snapshot into staging to repro a bug — the single most common real-world exposure of this pattern.

Fix — No prod→staging DB export path or credentials; staging seeded only by an automated synthetic-data script, as already stated in §03 — just remove the means to violate it.

Security verdict

The proposed architecture — managed auth, managed Postgres, managed hosting — is a sound foundation and avoids the highest-risk DIY-auth mistakes. It is not yet sign-off ready: the spec is silent on the one control that matters most for this product (server-side ownership enforcement on private gems), and the schema bakes in a future public-migration path for that same sensitive data with no described safeguard. Closing the top three findings is roughly 1–2 weeks of focused engineering plus an authorization test suite, layered into the Phase 0/1 work already planned in §08 — not a new phase.

Legal — ADA/WCAG liability

Requested directly: what legal responsibility does an app "owner" actually hold around WCAG, and does that responsibility — given this company's ownership status — permit softening or dropping any of the §11 accessibility findings that were treated as necessary for release? Per legal-risk:regulatory-compliance, chief-legal-and-risk-officer, enterprise-risk, and disputes-and-legal-holds. Read-only; research only, no files touched.
Short answer: no exemption applies, and the recommendation is not to soften anything on legal grounds. There is no codified rule forcing WCAG on a private company, but that gap is not a safe harbor — and "ownership status" (small, early-stage, any entity structure) does not change whether the ADA reaches this product, only who is personally exposed and how likely enforcement is today. Detail below.

Two different ADA titles were being conflated

The DOJ's 2024 rule formally mandating WCAG 2.1 AA is real, but it's a Title II rule — it binds state and local government entities only. It does not reach Flourish, a private consumer product. What actually applies here is Title III ("public accommodations"), and there is currently no codified DOJ regulation specifying WCAG — or any technical standard — for private Title III businesses; DOJ withdrew its earlier Title III rulemaking effort and hasn't replaced it.

That regulatory silence is not the same as no exposure. Federal courts — starting with Robles v. Domino's Pizza, and consistently since in Southern/Eastern District of New York practice (Andrews v. Blick Art Materials) — have held a commercial app or website tied to a business can itself be a "place of public accommodation" under Title III, physical storefront or not. In the near-total absence of a litigated technical standard, courts, settlements, and DOJ consent decrees use WCAG 2.1 AA as the de facto compliance benchmark anyway — plaintiffs plead against it, defendants settle to it, judges reference it. The exposure is common-law/litigation-driven rather than regulatory, which in practice is not materially smaller.

Does "ownership status" change the obligation? No.

Title III has no small-business, revenue, or entity-structure exemption. That carve-out exists only in Title I (employment discrimination, businesses under 15 employees) — a commonly confused point. Title III reaches any business open to the public regardless of size, and regardless of whether it's a sole proprietorship, LLC, or corporation.

Entity structure changes who is personally on the hook — an LLC/corporation shields an owner's personal assets from a judgment against the business; a sole proprietor is personally exposed directly — but it does not change whether the ADA reaches the product itself. Being pre-revenue or early-stage changes only the practical odds of being targeted today, not the legal standard, and that argument gets weaker the moment this goes from prototype to public launch.

New York-specific exposure

New York federal courts are the highest-volume jurisdiction in the country for ADA website/app accessibility filings — well ahead of the next closest state — and filings aren't limited to NYC; statewide plaintiffs' firms file broadly, so Rochester-based doesn't insulate the company. Separately, NY State and NYC Human Rights Law allow uncapped compensatory damages, unlike federal Title III, which caps out at injunctive relief plus attorney's fees — this is why NY plaintiffs' counsel increasingly favor state-law claims, and it raises the real stakes above a federal-only reading.

Addendum — does Title II's population-based rule extend here? No.

A follow-up question asked whether Title II's population-size distinction — some public entities get a longer compliance runway than others — could apply to Flourish, opening room to soften some §11 findings in exchange for easier delivery elsewhere. Checked directly against DOJ's rule and confirmed current as of this pass: that provision changes only the compliance deadline for entities Title II already covers. Public entities with population 50,000+ must conform by April 26, 2027; smaller public entities and special districts by April 26, 2028 (both dates extended once already from the original 2024 rule). Either way, the required technical standard is the same WCAG 2.1 AA — the population threshold never lowers the bar, only when it's due.

More to the point: Title II only reaches state and local government entities and their instrumentalities — which is exactly why public schools and universities are covered, as government bodies, not as a general "education" carve-out. A private educational institution isn't a Title II entity either; it falls under Title III, same as Flourish. There's no reading of this rule, direct or by analogy, that reaches a private consumer app. Net effect: no change to §11's findings or §14's gate.

Audio memo stays — and here is the reasoning, so it isn't relitigated

The owner has committed to it and §04/§08 already reflect that. It is a genuinely good feature: it captures the thing people actually want to record about a hidden place — tone, detail, the thought they'd never type — at the exact moment they're standing in it. Two conditions attach, both cheap:

1. The text notes field is not removable and does not get demoted behind the audio flow. This is what keeps audio memo an addition rather than a barrier. A user who can't hear their own recording, or can't speak into one, still has to be able to capture the same thing by the same route — and because that equivalent path already exists on the same form, audio memo clears §11 without a finding against it. Remove or bury the text field and the feature becomes an accessibility problem it currently isn't.

2. It inherits the private-gem security model in full — owner-scoped endpoints and signed expiring URLs, exactly as §12 specifies for gem photos. A voice recording attached to a private location is the most sensitive single artifact this product will ever store, and it should never have been on a list where photos were covered and audio wasn't.
